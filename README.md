# LIFE OS — 나를 위해 일하는 작은 AI 회사

GitHub와 Render의 **무료 플랜만으로** 운영하는 개인용 자율 에이전트 웹앱입니다.
사이트에 접속하면 직원 12명이 출근해서, 내가 등록한 일정·목표·기록을 살펴 할 일을 스스로 찾고, 허용된 범위에서 처리하고, 결과를 GitHub에 저장합니다. 사이트를 닫으면 멈추고, 다시 열면 멈춘 단계부터 이어서 합니다.

- 프론트엔드: React + TypeScript + Vite + Tailwind + Zustand + TanStack Query, Canvas 픽셀 사무실, PWA
- 백엔드: Python FastAPI (API + 화면 파일을 서비스 1개로 제공), SSE 실시간 상태
- 저장: GitHub 저장소의 전용 브랜치(`lifeos-data`) + 브라우저 IndexedDB
- AI: 브라우저 로컬 AI(WebLLM, 선택) → 없으면 규칙 기반 엔진만으로 동작

## 먼저 알아둘 것 (정직한 범위 안내)

**실제로 동작하고 자동 테스트로 확인한 것**

| 기능 | 내용 |
|---|---|
| 자동 출근·자율 업무 | 접속하면 세션 시작 → 직원 출근 → 데이터에서 업무 발견 → 우선순위(0~100점, 근거 표시) → 단계별 실행 |
| 규칙 기반 업무 18종 | 일정 충돌·일일 계획·밀린 일정 재배치, 복습·시험 계획, 집필 진도, 예산, 포트폴리오, 프로젝트 지연, 중복 자료, 생활 과부하, 아이디어 연결, 시스템 점검, 기록 정리, 문서 자동 작성 등 |
| 체크포인트·복구 | 단계가 끝날 때마다 저장. 새로고침·브라우저 종료·서버 재시작 뒤 끝난 단계는 건너뛰고 이어서 실행 |

| 문서 | 9종 문서를 실제 데이터로 작성, **DOCX / MD / HTML** 파일로 내려받기 |
| 회의 | 직원별 실제 데이터 분석으로 의견·결정·후속 업무 생성 (“규칙 기반 협업 보고서”로 표시) |
| 그 밖 | 인생 시뮬레이터(3가지 계획), 비상대책실, 디지털 분신(선호 기록), 직원 성장(경험치·레벨), 12개 화면 |

**한계 — 구현하지 않았거나 확인하지 못한 것**

1. **로컬 AI(WebLLM)는 코드만 연결되어 있고 실제 기기에서 검증하지 못했습니다.** 개발 환경에 WebGPU가 없어 모델 내려받기·추론을 실행해 볼 수 없었습니다. 서버 쪽 AI 작업 흐름(요청→결과 수신→저장, 미지원 시 대기)은 테스트했습니다. AI가 켜지지 않아도 나머지 기능은 모두 동작합니다.
2. **PDF 직접 생성 없음.** HTML로 내려받아 브라우저 인쇄에서 “PDF로 저장”을 쓰세요. (한글 글꼴을 무료·안정적으로 내장하는 방법을 넣지 못했습니다.)
3. **외부 무료 AI API 연결 화면 없음, 실시간 시세·공시 없음.** 투자 직원은 직접 입력한 현재가로만 계산하며 매매 기능은 없습니다. 웹 자료 조사는 위키백과 공개 API 하나만 지원하며 기본으로 꺼져 있습니다(모의 응답으로만 검증).
4. **사이트를 닫은 동안에는 '서버 예약 실행'을 켠 반복 규칙만 실행됩니다.** GitHub Actions가 6시간마다 서버를 깨워 실행시키고(아래 '서버 예약 실행'), 로컬 AI가 필요한 단계와 승인이 필요한 단계는 다음 접속까지 기다립니다.
5. **GitHub Actions 예약 실행은 보장되지 않습니다.** 정확한 시각에 시작되지 않으며, 저장소가 오래 비활성이면 예약이 꺼질 수 있습니다. 비공개 저장소·무료 계정에서 예약이 아예 실행되지 않는다는 사용자 보고도 있습니다. 실행되지 않아도 앱은 접속할 때마다 같은 점검(시스템 일일 점검)을 직접 합니다. Actions 탭에서 수동 실행(Run workflow)도 가능합니다.
6. **민감한 기억의 별도 암호화는 없습니다.** `DATA_ENCRYPTION_KEY`를 설정하면 전체 데이터가 암호화되어 GitHub에 저장됩니다. 설정하지 않으면 비공개 저장소에 평문으로 저장됩니다.
7. 단계 실행 타임아웃은 사후 기록만 합니다(규칙 단계는 수 ms 수준). 로컬 AI 추론은 120초, AI 작업은 300초 뒤 실패 처리됩니다.
8. 캐릭터 장식 해금은 배지·왕관 표시 수준이며 사무실 가구 꾸미기는 없습니다.
9. 모바일 점검은 자동화 브라우저(390×844)로만 했습니다. 실제 휴대폰에서는 확인하지 못했습니다.

## 에이전트 실행 엔진 (v2)

직원들이 대답만 하는 것이 아니라, 맡긴 일을 **계획 → 실행 → 검증**하는 구조입니다. 대시보드나 「🧭 업무 실행」 화면의 **맡기기** 입력창, 또는 직원 패널에서 명령합니다.

### 실행 단계
`GOAL(목표) → CONTEXT(기억 검색) → PLAN(계획) → EXECUTE(도구 실행) → OBSERVE(결과 관찰) → VERIFY(검증) → REVISE(수정) → COMPLETE(완료·결과 기억)`

- 한 번에 한 상태씩 전이하고 저장합니다. 브라우저가 닫히거나 서버가 재시작돼도 마지막 상태부터 이어갑니다.
- 모든 전이와 근거는 워크플로의 「실행 기록」에 남습니다. 각 단계에는 담당 직원, 입력(앞 단계 산출물과 그 해시), 도구, 선행 단계, 예상 산출물, 완료 기준, 실패 시 대응(다시 시도/건너뛰기/중단/사용자에게 묻기/앞 단계부터 수정), 최대 재시도, 제한 시간이 있습니다.
- 선행 단계가 끝나지 않으면 다음 단계로 넘어가지 않습니다. 같은 오류가 두 번 연속 나면 반복하지 않고 멈춘 뒤, 원인과 복구 방법(어느 단계부터 다시 할 수 있는지)을 기록합니다.

### 명령 예시와 계획

| 명령 | 계획 (담당) |
|---|---|
| 「임용 스터디 프로젝트 할 일 정리해줘: 역할 분담」 | 프로젝트 검색(마일로) → 할 일 도출: 명령 항목 + 확정 규칙의 기본 할 일 + 마감 전 점검·지연 작업(마일로) → **승인** → 할 일 생성·중복 검사(마일로) → 보고(루미) |
| 「주간 보고서 만들어줘」, 「이번 주 일정표 문서 만들어줘」 | 데이터 수집·본문(페이지) → DOCX 파일 생성 후 **저장소에서 다시 읽어** 존재·형식·열기·필수 내용 검사(페이지) → 다운로드 링크 보고(루미) |
| 「내일 오후 3시 팀 회의 1시간 잡아줘」 | 그날 일정 조회 → 충돌 검사 → 겹치면 **원래 시간과 가까운 대안 시간을 골라 달라고 요청** → 저장 → 저장·중복·충돌 재검사 |
| 「이번 주 일정 충돌 확인해줘」 | 7일 안의 충돌 쌍 찾기 → 중요도 낮은 쪽의 대안 제시 → 고른 시간으로 이동 |
| 「이번 주 발표 준비해줘」 | 아래 협업 예시 |
| 「IEP 연구 프로젝트 규칙: 리허설 3회 기억해줘」 | 확정 사실로 저장 → 다음 실행에서 검색되는지 바로 확인 |
| 「참고 자료 조사해줘」 | 내부 문서·기억(+켜져 있으면 위키백과) 수집, 중복 제거 → 자료 모음 DOCX |
| 「「오래된 메모」 삭제해줘」 | 대상 찾기 → **항상 승인**(위험도 HIGH) → 삭제 확인 |
| 「이번 달 예산 점검해줘」 | 기존 규칙 기반 업무로 바로 실행 |
| 그 밖의 자유 질문 | 기억·자료 검색 → 로컬 AI 답변 (AI가 없으면 그 단계는 건너뛰고 찾은 자료만 보고) |

명령 해석과 계획 작성은 키워드·날짜 해석 규칙과 템플릿으로 합니다. 작은 로컬 모델이 세운 계획은 검증하기 어렵기 때문입니다.

### 협업 예시 — 「이번 주 발표 준비해줘」
요청서의 예시 이름(아카·도티·세이프)은 기존 직원으로 맞췄습니다: 아카→**아카이**(자료 조사원), 도티→**페이지**(문서 제작자), 세이프→**픽스**(시스템 관리자).

1. 루미: 14일 안의 발표 일정·관련 목표 확인 → 주제·키워드
2. 아카이: 키워드로 내부 문서·기억(+위키백과) 수집, 출처·기준 시각 기록, 중복 제거
3. 아테나: 자료 본문에서 핵심어를 뽑고 근거 문장을 붙임 (통계 기반, AI 아님)
4. 아테나: 핵심 요약 — 로컬 AI가 있으면 AI, 없으면 추출 요약으로 대체하고 그렇게 표시
5. 페이지: 슬라이드 구성 (확정 규칙의 최대 장수 준수)
6. 페이지: DOCX 생성·검증
7. 픽스: 만들어진 파일을 다시 읽어 개념·출처·발표일 누락 검사 → 빠졌으면 5단계부터 보충해 다시 만듦
8. 루미: 발표 전 빈 시간에서 리허설 후보 계산 (등록하지 않고 제안만)
9. 루미: 보고

각 단계는 앞 단계의 실제 산출물을 입력으로 받고, 입력 해시가 앞 단계 출력 해시와 같은지 테스트로 확인합니다.

### 도구 (모두 서버의 실제 함수)
프로젝트 검색, 일정 조회·충돌 검사·충돌 찾기, 일정 생성·수정, 할 일 생성, 문서 본문 작성, 문서 생성·파일 저장, 문서 내용 검색, 파일 읽기·수정, 웹 자료 조사(위키백과), 기억 검색·저장, 통계 계산, 데이터베이스 조회(읽기 전용), 승인 요청, 기록 삭제 등 29개. 「업무 실행」 화면 아래에서 목록과 위험도를 볼 수 있습니다.
도구마다 검증 함수가 있습니다. 예: 일정 생성 → DB 저장·중복·충돌, 문서 → 파일 존재·형식·열기·필수 내용, 자료 조사 → 실제 출처·기준 시각·중복 제거.
**로컬 AI 모델은 도구를 직접 호출하지 않습니다.** 도구는 실행 엔진이 부르고, 모델은 「AI 문장 생성」 단계에서 문장만 씁니다.

### 기억
- 종류를 나눕니다: **확정 사실**(사용자가 정한 것), **AI 가설**, **실행 결과**(워크플로가 끝날 때 자동 저장)
- 프로젝트 작업에서는 그 프로젝트 기억과 공통 기억만 씁니다. 다른 프로젝트의 기억은 섞지 않습니다.
- 같은 「주제 키」의 확정 사실이 여러 개면 가장 최근 것만 쓰고, 나머지는 '대체됨'으로 기록합니다. AI 가설은 확정 사실을 덮지 못합니다.
- 태그에 `규칙`이 있는 확정 사실은 질의와 관계없이 항상 불러오고, 숫자 제약(슬라이드 ○장, 리허설 ○회, 마감 ○일 전, 자료 ○개 이상, 일정 ○분, `할 일: A, B`)을 읽어 실행에 반영합니다.
- 직원이 만든 일정을 사용자가 고치면 수정 내용을 확정 사실로 기억합니다. 일정 길이를 고치면 다음 일정의 기본 길이가 됩니다.

### 능동적 업무 발견 (제안 상태로만)
다음을 발견하면 「직원들의 제안」에 올립니다. **수락해야 실행**하고, 수락한 뒤에도 일정을 등록하기 전에 계획 승인을 한 번 더 받습니다.
- 14일 안에 발표가 있는데 그 전까지 리허설·연습 일정이 없음 → 리허설 시간 확보
- 14일 안에 시험이 있는데 하루 필요 학습 시간이 최근 평균보다 20% 이상 많음 → 복습 시간 확보
- 7일 안에 집필 마감이 있는데 원고가 미완성 → 집필 시간 확보
- 5일 안에 과제 마감이 있는데 관련 자료가 2건 미만 → 참고 자료 조사

### 로컬 AI 라우팅
- **WebLLM**(브라우저 안): 설정에서 켠 모델 1개. 필요한 메모리 1.5GB 이하는 경량, 그 이상은 상위 모델로 씁니다. 한국어를 잘하는 Qwen·Gemma 계열이 목록 위에 옵니다.
- **Ollama**(내 컴퓨터, 선택): 설정 › Ollama 연결에서 주소를 넣고 경량·상위 모델을 고릅니다. 브라우저가 직접 부르므로, Ollama 쪽 환경변수 `OLLAMA_ORIGINS`에 이 사이트 주소를 넣어야 합니다. Render 서버에서는 Ollama를 실행할 수 없습니다.
- 분류·요약·태그는 경량, 계획·분석·검증·답변은 상위 모델로 보냅니다. 경량 모델의 검증 통과율이 5회 이상 기록에서 70% 아래면 상위 모델로 바꿉니다. 같은 입력의 결과는 캐시해서 다시 추론하지 않습니다.
- 모델이 없으면 허용된 단계만 비AI 방식(추출 요약)으로 대체하고 그렇게 표시합니다. 대체할 수 없는 단계는 건너뛰거나 기다립니다.

### 성능 지표 (게임 경험치와 별개)
직원 패널의 「실제 성능」: 작업 성공률, 검증 통과율(첫 시도에 통과한 비율), 오류율, 평균 재시도, 사용자 수정률(직원이 만든 기록 중 사용자가 고친 비율), 평균 완료 시간, 만족도(결과 평가 별점). 규칙 기반 업무와 워크플로 단계를 모두 집계합니다.

### 서버 예약 실행 설정 (브라우저를 닫아도 실행)
1. Render › Environment에 `CRON_TOKEN`이 있는지 확인합니다 (Blueprint가 자동 생성. 직접 만든 서비스라면 긴 무작위 문자열을 넣습니다).
2. GitHub 저장소 › Settings › Secrets and variables › Actions › **New repository secret** 으로 두 개를 등록합니다.
   - `LIFEOS_URL`: `https://life-os-xxxx.onrender.com` (끝에 / 없이)
   - `CRON_TOKEN`: Render의 값과 똑같이
3. 앱 설정 › 자동화 설정 › 반복 업무 규칙에서 원하는 규칙의 **서버 예약 실행**을 켭니다.
4. Actions 탭 › LIFE OS 서버 예약 실행 › **Run workflow**로 한 번 실행해 보고, 다음 접속 때 재접속 보고서에 '서버 예약 실행' 줄이 생기는지 확인합니다.

알아둘 점: GitHub 예약 실행은 늦거나 빠질 수 있고, 무료 계정의 비공개 저장소에서는 예약이 돌지 않는다는 사용자 보고도 있습니다. 더 확실하게 하려면 cron-job.org 같은 무료 외부 예약 서비스가 같은 주소(`POST /api/cron/run`, 헤더 `X-Cron-Token`)를 부르게 하면 됩니다. 이 경우 토큰이 외부 서비스에 저장된다는 점을 감안하세요. 서버를 깨울 때마다 15분쯤 Render 무료 시간을 씁니다(6시간마다면 월 약 30시간).

### 이번 버전의 한계

## 배포 방법

### 1. GitHub 저장소 만들기
1. github.com 로그인 → 오른쪽 위 **+ › New repository**
2. 이름 `life-os`, **Private** 선택 → Create repository

### 2. 코드 올리기
받은 zip을 풀고, 저장소 화면의 **uploading an existing file**을 눌러 폴더 안의 내용을 모두 끌어다 놓습니다.
`.github` 폴더(숨김 폴더)도 반드시 포함하세요. `backend/static` 폴더(미리 빌드된 화면)도 그대로 올립니다.
Git을 쓴다면:
```bash
cd life-os
git init && git add . && git commit -m "LIFE OS"
git branch -M main
git remote add origin https://github.com/내아이디/life-os.git
git push -u origin main
```

### 3. 비밀 키 만들기
**(1) GitHub 토큰** — 앱이 데이터를 저장할 때 씁니다.
1. GitHub › 프로필 사진 › Settings › Developer settings › Personal access tokens › **Fine-grained tokens** › Generate new token
2. Repository access: **Only select repositories** → `life-os`만 선택
3. Permissions › Repository permissions › **Contents: Read and write** (다른 권한은 주지 않음)
4. 만료일을 정하고 생성 → `github_pat_...` 값을 복사해 둡니다. (만료되면 저장이 실패하니 새로 만들어 교체)

**(2) 암호화 문장** — 잊어버리지 않을 긴 문장을 하나 정합니다(예: 한글 문장 20자 이상). **잃어버리면 저장된 데이터를 열 수 없습니다.** 안전한 곳에 적어 두세요.

### 4. Render 무료 서비스 만들기
1. render.com 가입(GitHub 계정으로 로그인, 카드 등록 불필요)
2. **New › Blueprint** → `life-os` 저장소 연결 → `render.yaml`을 읽어 서비스가 준비됩니다.
   (Blueprint를 쓰지 않으려면 New › Web Service → 저장소 선택 → Root Directory `backend`, Build `pip install -r requirements.txt`, Start `uvicorn app.main:app --host 0.0.0.0 --port $PORT`, Instance Type **Free**)

### 5. 환경변수 설정
Render 서비스 › **Environment**에서:

| 이름 | 값 |
|---|---|
| `LIFEOS_GITHUB_REPO` | `내아이디/life-os` |
| `LIFEOS_GITHUB_TOKEN` | 3-(1)의 토큰 |
| `DATA_ENCRYPTION_KEY` | 3-(2)의 문장 |
| `SECRET_KEY`, `SETUP_CODE` | Blueprint가 자동 생성 (직접 만들 때는 긴 무작위 문자열을 넣기) |
| `LIFEOS_DATA_BRANCH` | `lifeos-data` (기본값) |

데이터는 `lifeos-data`라는 별도 브랜치에 저장됩니다. 코드 브랜치(main)와 분리되어 있어 데이터가 저장될 때마다 재배포되지 않습니다. 브랜치는 첫 저장 때 자동으로 만들어집니다.

### 6. 최초 배포
환경변수를 저장하면 배포가 시작됩니다. Logs에 `Uvicorn running`이 보이면 `https://life-os-xxxx.onrender.com` 주소로 접속합니다.

### 7. 사용자 인증 설정
1. 첫 화면에서 비밀번호(8자 이상)를 정합니다.
2. **설정 코드** 칸에는 Render › Environment의 `SETUP_CODE` 값을 복사해 넣습니다(주소를 아는 다른 사람이 먼저 비밀번호를 정하지 못하게 하는 장치).
3. 가장 중요한 목표 하나를 입력하면 사무실로 들어갑니다.

비밀번호는 scrypt로 해시해 저장하고, 로그인은 서명된 HttpOnly·SameSite=Strict 쿠키 + CSRF 토큰으로 보호합니다. 로그인 시도는 분당 6회로 제한됩니다. 비밀번호를 바꾸면 다른 기기의 로그인이 모두 풀립니다.

### 8. AI 모델 설정 (선택)
설정 › **로컬 AI 설정** › 사용 가능한 모델 찾기 › 켜기.
- WebGPU를 지원하는 브라우저(최신 Chrome·Edge 등)에서만 됩니다. 처음 켤 때 모델 파일(수백 MB 이상)을 내려받으니 Wi-Fi를 권장합니다.
- 켜지 않아도 됩니다. 꺼져 있으면 “규칙 기반 모드”로 표시되고, 규칙으로 해석할 수 없는 자유 지시만 대기 상태가 됩니다(완료로 위장하지 않음).

### 9. 에이전트 시작
따로 시작 버튼이 없습니다. **접속하면 시작**합니다.
1. 일정·목표, 기록 화면에서 일정, 학습 과목, 가계부 등을 입력합니다.
2. 직원들이 최소 60초 간격으로 데이터를 살펴 업무를 만들고 실행합니다. AI 사무실에서 캐릭터를 누르면 직원 패널(지시·일시정지·권한·로그)이 열립니다.
3. 승인이 필요한 업무는 위쪽 “승인 N” 배지와 업무 센터에 나타납니다.

### 10. 자동화 실행
- 접속 중: 자동. 설정 › 자동화 설정에서 일시중지·탐색 간격·반복 업무 규칙을 조절합니다.
- 미접속 중: `.github/workflows/maintenance.yml`이 하루 1회 데이터 정합성·백업을 점검해 `inbox.json`에 남기고, 다음 접속 때 “재접속 보고서”에 보여 줍니다. 암호화를 켰다면 저장소 › Settings › Secrets and variables › Actions에 `DATA_ENCRYPTION_KEY`를 같은 값으로 등록해야 내용까지 점검합니다(등록하지 않으면 형식만 확인).

### 11. 오류 대응
| 증상 | 확인할 것 |
|---|---|
| 첫 접속이 1분쯤 걸림 | 정상입니다. 무료 서버가 잠들었다 깨어나는 시간입니다. 그동안 입력한 내용은 기기에 보관했다가 자동 전송합니다. |
| 위쪽 배지 “저장 실패” | 설정 › 저장 상태의 오류 문구 확인. 대부분 토큰 만료·권한 부족(Contents: Read and write)·저장소 이름 오타 |
| “임시 저장” 배지 | GitHub 환경변수가 없어서 영구 저장이 안 되는 상태. 5단계를 확인 |
| “저장된 데이터가 암호화되어 있습니다” | `DATA_ENCRYPTION_KEY`가 빠졌거나 처음과 다름. 앱은 빈 데이터로 덮어쓰지 않고 멈춥니다. |
| 업무가 “막힘” | 카드에 이유가 표시됩니다(AI 없음 / 권한 없음 / 한도). 해결되면 자동 재개 |
| 업무 “실패” | 업무 카드 › 체크포인트부터 다시 시도. 여러 건이면 비상대책실 |
| 자동화가 멈춤 | 대시보드의 한도 안내 확인 → 설정 › 무료 한도 관리 |

### 12. 백업 및 복구
- 영구 저장에 성공하는 날마다 `snapshots/날짜.json` 스냅샷이 남습니다.

- GitHub의 `lifeos-data` 브랜치 커밋 기록에서도 예전 상태를 볼 수 있습니다.
